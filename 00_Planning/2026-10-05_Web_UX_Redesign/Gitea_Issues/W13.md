# [Web UX] Collect and expose message counts from approved real evidence sources

## Tracking
Work item: W13. Priority: P2. Parent: [EPIC #3](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/3).
Dependencies: [W12 #16](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/16), [W10 #14](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/14).
Implementation baseline: task/adore-web-interface; bootstrap records the remotely available commit. New specs/docs and acceptance copy are English.

## Problem and target behaviour
Implement message statistics only after the definition/capability issue is closed with recorded owner approval. Counts must come from real eligible evidence and expose unsupported sources honestly.

## Scope
Implement exactly the approved source and role/category semantics; do not broaden them silently. Prefer count-only metadata with source event identity, project/run identity and timestamp. Validate imported adapter output and persist deduplication/replay evidence safely.
Aggregate lifetime/in-period counts per job/project and separate executor/forge series, under the statistics scope contract. Unsupported executors/sources return unavailable with coverage; historical gaps are not synthetic zeros.
If the approved scope requires more than one bounded change, create implementation subissues before coding. No collection of conversation contents, live background polling or extra credential propagation unless the approved contract explicitly allows it.

## Acceptance criteria
- [ ] Owner-approved definition and supported sources are linked in the AEGIS requirement and tests.
- [ ] Happy-path fixtures from each implemented source yield the documented counts per role/category/job/project/period.
- [ ] Retry/replay/duplicate events and same run IDs across projects do not double count or misattribute.
- [ ] Unknown/malformed source output, timestamps, schema and identity associations fail closed.
- [ ] Unsupported/partial/historical coverage is visible; launches/model calls remain separately named.
- [ ] Late arrival/backfill/rebuild is idempotent and uses documented time attribution.
- [ ] API/UI/export preserve project RBAC and never leak message contents or financial data.
- [ ] No real executor/forge network calls or paid models run in automated tests.

## Verification
Source-level happy/negative contract tests, deterministic aggregate/replay fixtures and offline browser unavailable/partial/known series. Document source-specific limitations; a generic counter mock is not proof that an executor emits the approved evidence.

## Code and documentation orientation
Approved executor/forge evidence adapters, journal/usage aggregation, web metrics views and Statistics UI; offline fixtures; Component_Executor_Launcher/Forge_Adapters/Metrics/Web_API/Frontend as affected.

## Agent implementation contract
Read repository AGENTS.md, the full .agentic/AGENTS.md, relevant context and component contracts before product implementation. Use AEGIS for code, tests and implementation validation, with its resolved interaction mode and checkpoints. Ticket creation and standalone planning do not use AEGIS.
Start only after native blockers are closed, explicit decision gates are satisfied and the operator authorizes pickup. Never treat label priority or issue closure as publication approval.
Bound each run to at most four hours, three fix/review cycles and twenty hand-authored changed files (generated static output tracked separately); record an explicit cost/executor budget before launching executors. If the scoped work exceeds a bound, report/split rather than silently expand it.
Every public behaviour needs a happy test and negative trust-boundary tests. Keep unit tests offline, fail closed on corrupt input, preserve CSRF/RBAC/secret redaction, forge/executor/runtime independence and draft-only publication. No merge.
Update affected 05_SoftwareDocu component pages from the template, implementation-facing/operator docs, applicable AEGIS knowledge and CHANGELOG.md in the same change. Preserve license headers and Code_Style.md conventions. No speculative version bump or new dependency without a scoped justification.
For verification use the published baseline instructions: from 04_Software, uv run pytest and uv run ruff check .; from 04_Software/web, npm run typecheck, npm run build and npm run validate. Run targeted tests during development and the full required suite at validation; report actual results and limitations.
