# [Web UX] Create users with explicit role and project access in one reviewed operation

## Tracking
Work item: W14. Priority: P2. Parent: [EPIC #3](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/3).
Dependencies: [W01 #5](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/5), [W02 #6](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/6).
Implementation baseline: task/adore-web-interface; bootstrap records the remotely available commit. New specs/docs and acceptance copy are English.

## Problem and target behaviour
Current user creation and project assignment are separate operations. Make access part of the reviewed account-creation intent, without a partially created or overprivileged account.

## Scope
UI: identity/credentials -> role and projects -> review. Admin receives all-project/system access; Dev maps to the existing developer backend role and receives explicitly selected stable project IDs. Use current password/session mechanisms, not invented email invitations.
Provide an atomic create-user-with-grants server operation while preserving existing APIs where compatible. Validate project existence/visibility and race conditions on the server; rollback on failure. Access editing shows before/after and result.
Retain password hashing, session/CSRF protections, last-admin safety and disabled-user rules. Display names never substitute for grant identities.

## Acceptance criteria
- [ ] Valid admin/dev creation assigns exactly the reviewed privileges and grants atomically.
- [ ] Invalid/duplicate username, invalid role/password, unknown/archived or concurrently deleted project and invalid grants reject without partial user creation.
- [ ] Selecting admin makes all-project access explicit; Dev with no projects is an explicit reviewed choice rather than accidental success.
- [ ] Only admin can create/disable/reset/edit grants; last-admin safety and disabled sessions remain enforced.
- [ ] Passwords never appear in audit, logs, issue comments, persistent browser drafts or review values.
- [ ] Role/project UI does not weaken server enforcement; direct URL/API attempts cannot discover other projects or admin/cost functions.
- [ ] Current supported authentication/reset operations continue; no email/invite service is introduced.

## Verification
Offline transactional rollback/race and role/CSRF/disabled/last-admin negatives, grant changes and browser correction/review. Recheck new multi-project endpoints with project-scoped users; avoid implementation-only SQL helper tests.

## Code and documentation orientation
