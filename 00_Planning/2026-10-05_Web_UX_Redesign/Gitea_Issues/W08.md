# [Web UX] Rework project hubs, attention queues and job details around the next action

## Tracking
Work item: W08. Priority: P1. Parent: [EPIC #3](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/3).
Dependencies: [W01 #5](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/5), [W07 #11](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/11).
Implementation baseline: task/adore-web-interface; bootstrap records the remotely available commit. New specs/docs and acceptance copy are English.

## Problem and target behaviour
A user sees status/stage but has to infer why work stopped and where to intervene. Present current state, evidence, responsible actor and next action directly.

## Scope
Overview foregrounds Needs attention and explicitly scoped current-state cards. Project list separates pickup state from environment verification. Project hub: Summary, Jobs, Statistics, Settings, Access, History, with role-appropriate tabs.
Global jobs: ticket/title, project, lifecycle/reason, latest activity, known duration/consumption and simple filters; advanced executor/stage/outcome filters are secondary. Manual start is contextual and explains its effect.
Job details show What is happening now / Who acts / Where / What follows, then timeline, artifacts and technical details. Preserve exact lifecycle/stage mapping and quick-path omitted steps. No invented progress percentage.

## Acceptance criteria
- [ ] Clarification links to the ticket; candidate approval links to its actual forge location; in-review links to a draft MR/PR.
- [ ] Pickup stopped explicitly says active jobs continue; no arbitrary job Pause/Resume or UI merge/approval control exists.
- [ ] done is not labeled Merged unless there is evidence of a human merge; handoff states retain their distinct meaning.
- [ ] Retry/cancel/manual start reuse permitted command contracts, explain effects and show async result/errors rather than instant-success guesses.
- [ ] Scope, missing evidence, stale activity and worker status are visible; unknown telemetry remains unknown.
- [ ] Unauthorized projects/actions are excluded from navigation and rejected on direct routes/API.
- [ ] Empty, loading, failed and incomplete states are distinct; filters/search use the server read model.
- [ ] Existing URL/deep-link behaviour remains usable with the selected project/job context.

## Verification
Offline browser flows for every lifecycle group, stale/missing evidence, authorization, failed async command, quick path, search/paging and 390px/keyboard layout. Check actual labels against the backend contract, not synthetic fixture stage combinations.

## Code and documentation orientation
Overview, Projects and Jobs React pages; i18n/routes; job API types; offline browser scenarios; Component_Web_Frontend and operator workflow documentation.

## Agent implementation contract
Read repository AGENTS.md, the full .agentic/AGENTS.md, relevant context and component contracts before product implementation. Use AEGIS for code, tests and implementation validation, with its resolved interaction mode and checkpoints. Ticket creation and standalone planning do not use AEGIS.
Start only after native blockers are closed, explicit decision gates are satisfied and the operator authorizes pickup. Never treat label priority or issue closure as publication approval.
Bound each run to at most four hours, three fix/review cycles and twenty hand-authored changed files (generated static output tracked separately); record an explicit cost/executor budget before launching executors. If the scoped work exceeds a bound, report/split rather than silently expand it.
Every public behaviour needs a happy test and negative trust-boundary tests. Keep unit tests offline, fail closed on corrupt input, preserve CSRF/RBAC/secret redaction, forge/executor/runtime independence and draft-only publication. No merge.
Update affected 05_SoftwareDocu component pages from the template, implementation-facing/operator docs, applicable AEGIS knowledge and CHANGELOG.md in the same change. Preserve license headers and Code_Style.md conventions. No speculative version bump or new dependency without a scoped justification.
For verification use the published baseline instructions: from 04_Software, uv run pytest and uv run ruff check .; from 04_Software/web, npm run typecheck, npm run build and npm run validate. Run targeted tests during development and the full required suite at validation; report actual results and limitations.
