# [Web UX] Build guided project enrollment with explicit verification and review

## Tracking
Work item: W03. Priority: P1. Parent: [EPIC #3](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/3).
Dependencies: [W01 #5](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/5), [W02 #6](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/6).
Implementation baseline: task/adore-web-interface; bootstrap records the remotely available commit. New specs/docs and acceptance copy are English.

## Problem and target behaviour
The current enrollment form presents infrastructure fields together without explaining what the user is creating. Introduce a six-step task-based flow with visible instructions and a final review.

## Scope
Steps: method -> repository/identity -> working environment -> eligibility/reviewers/limits -> verification -> review/create. Initially expose only implemented methods; portable settings and clone options become active with their delivering issue.
Explain that the local clone folder is on the ADORE server and must already contain the repository. Require actual supported platform, owner/repo identifier, branch, executor/provider/model, runtime/image and authentication reference. Do not implement automatic repository cloning or accept unsupported URL parsing.
Start with honest explicit environment choices. Offer presets only if a real validated inventory exists; do not invent installed images or providers. Advanced options expose existing supported configuration. Structural validation is separate from an explicitly initiated environment probe, with an effect summary before the probe.
Keep the draft in memory, preserve Back/correction values and warn on navigation loss. No durable draft API or localStorage secrets in this scope.

## Acceptance criteria
- [ ] Visible instructions explain every mandatory concept without requiring prior AEGIS/ADORE knowledge.
- [ ] Back and review Change links retain entries; changing upstream choices invalidates dependent checks.
- [ ] Field and summary errors point to the corrective step and move focus accessibly.
- [ ] An explicit review lists identity, repository, environment, rules/limits, reviewers and server locations.
- [ ] Confirmation submits exactly the reviewed draft/revision and prevents accidental double creation.
- [ ] Completion states that pickup is stopped; activation is a separate explicit action and does not promise a specific ticket will start.
- [ ] Invalid configuration blocks creation; readiness failure is explained with a recheck action and cannot be hidden behind a successful badge.
- [ ] No secrets, browser-machine paths masquerading as server paths, fake presets or disabled-feature promises.

## Verification
Offline E2E valid enrollment, empty/malformed fields, ID collision, invalid clone/runtime, failed/stale readiness, changed upstream choice, back/review correction, double submit, Dev denial and refresh/navigation-loss scenarios. Verify keyboard/focus and 390px layout.

## Code and documentation orientation
Frontend enrollment page/components, API types, i18n and route handling; existing POST /projects and readiness contracts; browser fixtures; Component_Web_Frontend and operator setup guidance.

## Agent implementation contract
Read repository AGENTS.md, the full .agentic/AGENTS.md, relevant context and component contracts before product implementation. Use AEGIS for code, tests and implementation validation, with its resolved interaction mode and checkpoints. Ticket creation and standalone planning do not use AEGIS.
Start only after native blockers are closed, explicit decision gates are satisfied and the operator authorizes pickup. Never treat label priority or issue closure as publication approval.
Bound each run to at most four hours, three fix/review cycles and twenty hand-authored changed files (generated static output tracked separately); record an explicit cost/executor budget before launching executors. If the scoped work exceeds a bound, report/split rather than silently expand it.
Every public behaviour needs a happy test and negative trust-boundary tests. Keep unit tests offline, fail closed on corrupt input, preserve CSRF/RBAC/secret redaction, forge/executor/runtime independence and draft-only publication. No merge.
Update affected 05_SoftwareDocu component pages from the template, implementation-facing/operator docs, applicable AEGIS knowledge and CHANGELOG.md in the same change. Preserve license headers and Code_Style.md conventions. No speculative version bump or new dependency without a scoped justification.
For verification use the published baseline instructions: from 04_Software, uv run pytest and uv run ruff check .; from 04_Software/web, npm run typecheck, npm run build and npm run validate. Run targeted tests during development and the full required suite at validation; report actual results and limitations.
