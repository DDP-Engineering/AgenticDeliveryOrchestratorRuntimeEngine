# [Web UX] Specify message-count semantics and executor/forge source capabilities

## Tracking
Work item: W12. Priority: P2. Parent: [EPIC #3](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/3).
Dependencies: [BASE #4](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/4).
Implementation baseline: task/adore-web-interface; bootstrap records the remotely available commit. New specs/docs and acceptance copy are English.

## Problem and target behaviour
There is no proven message-count data contract in the current implementation. Executor launches, model calls and usage events are different quantities. Define the requested measurement before implementing collection.

## Scope
Recommend separate executor conversation messages and forge comments, without an implicit mixed total. Specify whether the count includes human, assistant and tool messages, comments received/posted, retries and revision rounds. Identify what each supported executor/platform can actually supply, including no/partial capability.
Define event identity/source, project/run association, timestamp/role/category, deduplication, replay, late arrivals, completeness and retention/privacy. Do not collect message contents merely to count them.
Evaluate existing persisted evidence and documented adapter outputs. Do not use live user credentials, contact real forge projects, scrape conversations or perform paid executor runs without separate operator authorization.
Provide fixtures/examples, unavailable/unknown behaviour, API/aggregation contract and compatibility impact. Record unresolved decisions and request owner approval on this issue.

## Acceptance criteria
- [ ] An English definition distinguishes messages, model calls, executor launches and usage events.
- [ ] A capability matrix covers all currently supported executor and forge adapters; unavailable evidence is explicit.
- [ ] Examples define expected counts for retry/replay, tool traffic, cross-period jobs and received/posted comments.
- [ ] Privacy, authority, deduplication and timestamp gaps are addressed without inventing telemetry.
- [ ] The repository owner approves the chosen definition/source scope in the issue; approval is a prerequisite for collection implementation.
- [ ] No runtime code or state is changed by this planning ticket.
