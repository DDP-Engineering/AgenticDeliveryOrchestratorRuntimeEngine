# [Web UX] Make exact host-specific TOML enrollment understandable and revision-safe

## Tracking
Work item: W04. Priority: P1. Parent: [EPIC #3](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/3).
Dependencies: [W03 #7](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/7).
Implementation baseline: task/adore-web-interface; bootstrap records the remotely available commit. New specs/docs and acceptance copy are English.

## Problem and target behaviour
The current Import project screen is short but assumes knowledge of config.toml, server paths and unchanged copying. Present this as an advanced exact enrollment mode, distinct from future portable settings transfer.

## Scope
Name the action Enroll an existing configuration for this ADORE server. Explain where the TOML comes from, which paths belong to the server, that bytes are copied unchanged and that the file alone does not transfer historical jobs.
Steps: file -> declared identity/paths -> structural validation -> explicit environment checks where supported -> review -> enroll with pickup stopped. Preview repository, worktree, state and metrics locations and recognized agent/runtime settings. Use structured issues linked to fields/locations.
Preserve the existing preview/confirmation revision binding, server-side reinspection, state lock, inactive-run requirement, path ownership and secret checks. Offer no silent path rewriting in exact mode. Adapt for a new server is a separate portable flow once available.

## Acceptance criteria
- [ ] A novice can identify the file source, unchanged-copy behaviour, server location requirements and pickup-stopped result from visible text.
- [ ] Review shows all consequential locations and effects without exposing secrets.
- [ ] Invalid TOML, secret-bearing input, relative paths, volume roots, overlapping state ownership, active/corrupt state and duplicate identities fail closed.
- [ ] File changes after preview and concurrent ownership/lock changes reject confirmation rather than apply an unreviewed candidate.
- [ ] Successful import preserves exact configuration bytes and existing history only where underlying data already exists.
- [ ] Back/correction preserves the draft but invalidates stale preview; import failures never look like success.
- [ ] Dev and missing/invalid CSRF requests cannot preview or enroll administrator-only configuration.

## Verification
Extend offline import tests for successful exact-copy/pause, every listed trust boundary, failed readiness and stale preview; add browser explanatory-review and correction paths. No live forge or container probes in automated tests.
