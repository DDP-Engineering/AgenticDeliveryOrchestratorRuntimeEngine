## Problem and target behaviour
A guided interface is not proven self-explanatory by a mockup or green unit suite. Validate the integrated product and record actual novice-user findings before closing the epic.

## Scope
Add meaningful offline E2E scenarios across enrollment, exact/portable import, cloning, blocked/stale settings review, all job waiting/result states, statistics scope/coverage, user grants and audit. Reuse isolated fake-boundary server/worker; no real forge/docker/git/executor commands in tests.
Verify keyboard/focus, field errors/status announcements, light/dark contrasts, responsive reflow at 390px, readable charts/tables and direct links. Target WCAG 2.2 AA; record manual gaps instead of claiming certification from tooling.
Conduct observed acceptance tasks with five people unfamiliar with ADORE/AEGIS, in a safe prepared environment. The implementation agent can prepare the session and fixtures but must not invent participants, timings, approvals or findings. Owner arranges unavailable human sessions; report the gate as pending until genuine evidence exists.

## Acceptance criteria
- [ ] Full offline Python and frontend validation passes; meaningful negative trust boundaries are covered and existing contracts preserved.
- [ ] At least 4/5 participants explain pickup stopped versus waiting for clarification within one minute without coaching.
- [ ] At least 4/5 enroll a prepared-environment project within ten minutes without verbal instruction; infrastructure setup time is separate.
- [ ] At least 4/5 identify where candidate approval happens and understand ADORE never merges.
- [ ] At least 4/5 identify portable import inclusions/exclusions and required target values.
- [ ] Every participant can inspect the proposed change before apply and return to correct an enrollment choice.
- [ ] Project/period/timezone changes consistently scope cards, charts, tables and export; unavailable data differs from zero.
- [ ] Dev cannot bypass project restrictions or access financial/admin features through direct routes/API/export.
- [ ] Findings and unresolved accessibility/usability gaps have reproduction/evidence and follow-up ownership; no fabricated acceptance success.

## Verification and delivery
Run the repository's required AEGIS validation plus documented pytest/Ruff/frontend type/build/helper/E2E checks. Use the agreed release-candidate baseline, deterministic fixtures and manual keyboard/screen-reader/contrast inspection where needed. Live acceptance probes remain operator-authorized.
Deliver an English report of observed results and limitations, final operator guidance and changelog. Publication is draft-only and human-approved. If human evaluation is unavailable, finish technical evidence but keep the human acceptance/epic gate open.

## Agent implementation contract
Read repository AGENTS.md, the full .agentic/AGENTS.md, relevant context and component contracts before product implementation. Use AEGIS for code, tests and implementation validation, with its resolved interaction mode and checkpoints. Ticket creation and standalone planning do not use AEGIS.
Start only after native blockers are closed, explicit decision gates are satisfied and the operator authorizes pickup. Never treat label priority or issue closure as publication approval.
Bound each run to at most four hours, three fix/review cycles and twenty hand-authored changed files (generated static output tracked separately); record an explicit cost/executor budget before launching executors. If the scoped work exceeds a bound, report/split rather than silently expand it.
Every public behaviour needs a happy test and negative trust-boundary tests. Keep unit tests offline, fail closed on corrupt input, preserve CSRF/RBAC/secret redaction, forge/executor/runtime independence and draft-only publication. No merge.
Update affected 05_SoftwareDocu component pages from the template, implementation-facing/operator docs, applicable AEGIS knowledge and CHANGELOG.md in the same change.
