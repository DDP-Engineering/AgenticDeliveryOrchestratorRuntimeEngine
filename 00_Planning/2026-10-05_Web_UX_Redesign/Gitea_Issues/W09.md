# [Web UX] Organize project settings by purpose and review candidate changes before applying

## Tracking
Work item: W09. Priority: P1. Parent: [EPIC #3](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/3).
Dependencies: [W01 #5](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/5).
Implementation baseline: task/adore-web-interface; bootstrap records the remotely available commit. New specs/docs and acceptance copy are English.

## Problem and target behaviour
Raw TOML keys and staged values do not make the impact of a setting clear. Present settings by user intent and show the current-to-proposed difference before applying.

## Scope
Categories: Repository and tickets; Agent and model; Isolated environment; Rules and approvals; Limits and recovery; Measurement and notifications; Advanced. Derive type, default, range, editability and allowed choices from the authoritative catalog.
Visible help explains purpose, units and consequence. Raw technical keys stay available in details/copy. Preserve developer redacted read-only access.
Flow: edit -> prepare candidate -> review before/after and conditions -> explicit apply/discard. In this ticket retain the existing single-setting candidate and supported endpoint edit behaviour; a multi-edit atomic candidate is a separate extension.
Use server revisions for conflict detection. Display reasons for blocked apply (active work/lock and paused-pickup requirements for identity/runtime changes), actor/time where recorded and honest fallbacks otherwise.

## Acceptance criteria
- [ ] Every editable setting has an understandable English label and essential visible help; actual/default/proposed are distinct.
- [ ] Review shows current and proposed values, affected project and effect; no secret is exposed in diff or copy.
- [ ] Preparing a candidate leaves active configuration unchanged; apply targets the exact reviewed candidate/base revision.
- [ ] Invalid types/limits, stale base/candidate, changed endpoint protocol/credentials and lock/active-work conflicts fail closed with useful recovery text.
- [ ] Identity/runtime changes retain paused-pickup requirements; all pending apply retains idle/lock protections.
- [ ] UI never promises multiple staged fields when the backend only supports one.
- [ ] Dev cannot mutate via UI or API; read-only categories do not disclose financial or secret data.
- [ ] Discard explicitly removes only the candidate, preserving active config.

## Verification
Existing offline pending-config/config-catalog tests plus before/after, sensitive-field redaction, no-active-write, stale revision, idle/lock/pause, direct API RBAC and browser correction/discard/blocked-apply scenarios.

## Code and documentation orientation
Settings catalog and frontend SettingsList/config pages; web/app.py pending config routes if projection needed; test_web_pending_config.py, test_web_setting_catalog.py and E2E; Component_Config_Edit/Web_API/Frontend docs.
