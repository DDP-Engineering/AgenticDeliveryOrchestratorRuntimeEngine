# [Pi] Provider, model, API key and OpenAI-compatible endpoint setup

Labels: P1, enhancement. Part of [epic #50](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/50). Depends on: [PI-03 #53](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/53).

## Goal

A user configures the agent with a provider, a model and a credential: an API key
for one of Pi's providers, or an OpenAI-compatible endpoint (LM Studio, Ollama,
vLLM). "Test AI connection" proves it works. The ChatGPT option appears but is
completed in PI-05.

## Decisions

- Configuration schema from `PLAN.md` section 4.2 (`[executor] provider, model,
  internet`, `[executor.endpoint] base_url, api`), with Pi's exact names from
  `SPIKE_FINDINGS.md`. Unknown or removed keys are refused.
- API keys live in the project's existing credential store, never in `config.toml`,
  and reach Pi as the environment variable Pi defines for that provider.
- For `provider = "custom"` ADORE generates Pi's `models.json` in the ADORE-owned
  agent directory; an endpoint key, if any, goes through the credential store.
- The provider list is Pi's API-key providers plus "OpenAI-compatible endpoint" and
  "ChatGPT subscription"; the model list comes from Pi (method from the spike),
  free text allowed.
- Changes go through the existing pending-candidate review and apply flow.

## Scope

In: config schema and validation; Settings -> Agent and model; enrollment step 2;
credential store wiring for the provider's variable; `models.json` generation;
"Test AI connection" for Pi over RPC (a model reply plus a shell command that
echoes a nonce, as today) with clear errors for an invalid key, an unreachable
endpoint and an unknown model; container access to a host endpoint (document
`host.docker.internal` or the configured address).

Out: ChatGPT sign-in (PI-05), internet switch (PI-06), server install (PI-07).

## Where to look

`adore/config.py`, `config.example.toml`, `adore/web/app.py` (settings, pending
config, credentials routes), `adore/web/executor_settings.py`,
`adore/web/model_connection.py`, `web/src` settings and enrollment components,
`tests/test_web_pending_config.py`, `tests/test_model_connection.py`,
`web/e2e/settings.spec.ts`, `web/e2e/enrollment.spec.ts`.

## Acceptance criteria

- [ ] The schema validates; unknown keys and removed executor keys are refused with
      the key named.
- [ ] Settings and enrollment show provider, model and credential fields in four
      locales with help; review and apply work as for other settings.
- [ ] A custom endpoint produces the `models.json` the spike proved; a fake-process
      test checks the file and the environment passed to Pi.
- [ ] "Test AI connection" reports success, invalid key, unreachable endpoint and
      unknown model distinctly (offline tests with a fake Pi).
- [ ] Keys never appear in `config.toml`, logs, audit rows, API responses or the
      browser (tests).
- [ ] Docs, help, `CHANGELOG.md` and release note updated.
