# [Pi] Pi installed on the server through an ADORE-managed installation

Labels: P2, enhancement. Part of [epic #50](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/50). Depends on: [PI-02 #52](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/52), [PI-03 #53](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/53).

## Goal

When a project runs on the server instead of a container, ADORE uses a Pi it
installed itself, at the pinned version, isolated from the account's personal Pi
configuration, on Linux and Windows.

## Decisions

- ADORE installs the pinned Pi into its own prefix (for example
  `<ADORE home>/tools/pi/<version>`) with `npm`, using a Node that meets Pi's
  minimum; an older or missing Node is refused with a clear message.
- ADORE never uses a globally installed Pi or the account's `~/.pi`; the agent
  directory is ADORE-owned (method from the spike).
- Local settings shrink to the account (current) and an optional PATH for project
  tools; the launch command is not configurable.
- Pi has no permission prompts: the interface recommends a dedicated OS account.
- Windows is in scope now, together with Linux (owner decision, 2026-11-01).

## Scope

In: install and verify (CLI command and readiness check), upgrade when the pinned
version changes, isolation, the local backend using `pi_rpc`, Windows specifics
(PowerShell tool, Node path), interface and help for the reduced local settings.

Out: container runs (PI-02), internet switch enforcement (not possible locally;
PI-06 shows it as not enforced).
