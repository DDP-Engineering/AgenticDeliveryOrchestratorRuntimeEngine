# [Direct] Verification command and bounded fix attempts

Labels: P1.

Part of [epic #60](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/60). Depends on: [DW-02 #62](http://192.168.1.15:3001/dpasare/AgenticDeliveryOrchestratorRuntimeEngine/issues/62).

## Goal

A project may configure one verification command. ADORE runs it after Pi finishes a
direct run, sends failures back to Pi a bounded number of times, and shows the
result to the approver.

## Decisions

- **The setting.** `[workflow] verify_command` is a string, empty by default. It
  holds one shell command line, run from the worktree root in the run's execution
  environment:
  - container: `sh -c` inside the run container;
  - local backend: the platform shell.

  The validate stage limit bounds it (`stage_timeout_overrides.validate`, else
  `per_gate_timeout_seconds`).
- **Refused values.** A non-string value, a multi-line value or a NUL character is
  refused with the key named. An empty value means "not configured".
- **Order of a direct run.** The build session meets DW-02's done conditions, then
  the stage becomes `validate` and ADORE runs the command.
- **Evidence.** Command, exit code, duration and the last 200 lines of output,
  passed through the existing sanitiser. It is stored as the run's
  `validation_evidence`.
- **Pass.** The run continues as in DW-02: checkpoint commit, fingerprint,
  `done`, `awaiting-approval`.
- **Failure or timeout.**
  - The stage returns to `build` and a fresh Pi session receives the command, exit
    code and output tail as failure context.
  - Attempts are bounded by `[recovery] max_stage_failures`. After the last one the
    run fails with `VERIFICATION_FAILED`, the last evidence is kept, and
    `adore retry` re-arms the run as today.
  - A command that hits its limit counts as a failed attempt, with "timed out"
    evidence.
- **Prompt.** When a command is configured, the direct prompt names it and asks Pi
  to run it before finishing.
- **Ticket and MR/PR texts.** The approval comment and the MR/PR body show the
  command and its result. With no command, they keep DW-02's "unverified" line.
- **AEGIS runs ignore `verify_command`.** They use the repository's AEGIS commands.
  The configuration reference says so.

## Done when

- [ ] A passing command leads to `awaiting-approval`. Its evidence is in the run,
      the approval comment and the MR/PR body.
- [ ] Failing once, then passing: the second Pi session receives the failure
      context, and the final evidence is the pass.
- [ ] Always failing: `VERIFICATION_FAILED` after `max_stage_failures` attempts,
      with the evidence kept. `adore retry` re-arms the run.
- [ ] A command timeout counts as a failed attempt with "timed out" evidence.
- [ ] Configuration negatives: non-string, multi-line and NUL values are refused
      with the key named. Empty is accepted.
- [ ] AEGIS runs are unaffected by `verify_command` (test).
- [ ] Documentation, `CHANGELOG.md` and a four-locale release note are updated.
      The journal records `release-notes: added` and
      `help: none (the setting appears in the interface in DW-04)`.

## Stop and ask (questions file) if

- Running a shell command line through the existing execution backends needs a
  new backend operation, rather than a use of the existing command execution.
- Fix attempts cannot share the existing `max_stage_failures` accounting without
  changing AEGIS runs.

## Working rules

- **Workflow and authority.** ADORE runs this ticket as one AEGIS task in this
  repository. Follow `AGENTS.md`, which is authoritative, and `.agentic/AGENTS.md`.
  The plan is `00_Planning/2026-11-10_Direct_Workflow_Without_AEGIS/PLAN.md`; read
  its sections 1 and 4.
- **Conflicts.** If this ticket conflicts with the plan, or the code has moved so a
  decision no longer fits, ask in the questions file instead of deciding.
- **AEGIS files.** `04_Software/adore/aegis.py` is ADORE's own AEGIS client and may
  be edited when needed. Never edit the AEGIS payload under `.agentic/`
  (`aegis.py`, `steps/`, `templates/`, `aegis.toml`).
- **Stored data.** No migrations or compatibility with earlier builds.
- **Documentation in the same change.**
  - A user-visible change needs `CHANGELOG.md` and a four-locale entry in
    `04_Software/adore/release_notes.toml`.
  - An interface or workflow change needs help in all four locales.
  - Component pages in `05_SoftwareDocu/` are updated too.
- **Tests.** Every public behaviour gets one happy test and negative tests at its
  trust boundaries. Tests run offline, using the existing fakes.
- **Test runs.** Run targeted tests while building; the full suite runs once, in
  validate, through the AEGIS strict check.
- **Style.** LF line endings, license headers, `01_Documentation/Code_Style.md`.
- **Git.** ADORE commits, pushes and opens the PR; never do these yourself.
