## Frame

Problem: In containers ADORE runs Pi 0.80.3 as `pi -p --mode json {prompt}`
(OBSERVED `04_Software/docker/Dockerfile.executor-base:25`,
`adore/executor/launcher.py` PiExecutor). Its push/forge guard is the
project's `.pi` extension, which headless Pi loads only after the project is
trusted, and ADORE never trusts it (OBSERVED launcher comment; SPIKE_FINDINGS
5). Usage is parsed from captured output after the launch (OBSERVED
`_extract_usage_detail`).
Desired outcome: The executor image ships Pi 1.4.0, pi-web-access 0.46.0 and
Node 22.23.4, and ADORE drives one `pi --mode rpc --no-session` process per
stage in the container, isolated from personal Pi resources, with an
ADORE-owned guard loaded explicitly, bounded memory, abort on timeout or
cancel, failures mapped to ADORE's codes and usage summed per turn (STATED
ticket #52 Goal/Decisions; findings "Pinned versions", items 5-6).
Actors: the orchestrator (stage launch), PiExecutor, Pi in the run container,
the operator who cancels a run, the administrator reading Statistics.
Primary scenario: a stage launch starts Pi through the container exec seam
with stdin open, sends the stage prompt, streams events until
`agent_settled`, records usage of every assistant turn, and returns a GateRun
the orchestrator already understands.
Examples: a stage with four turns and three tool calls returns exit 0 and the
summed tokens 1819/141 in, out, 3456 cache-read (OBSERVED fixture
run_tool_calls_chatgpt.jsonl); a stage over its timeout is aborted and the
process is gone within the grace period; `git push` in the bash tool is
refused by the guard (OBSERVED fixture run_guard_blocks_forge.jsonl).
Counterexamples: a native local Pi run keeps its current file-protocol launch

connection probe is unchanged (PI-04).

## Design

**Approach.** New `adore/executor/pi_rpc.py` exposes `run_pi_rpc(spawn,
argv, env, prompt, *, timeout, cancelled, output_path, stderr_path, redact,
graces) -> PiRpcResult`. It spawns one process with binary pipes, sends the
prompt through a writer thread, and parses stdout in a reader thread into
small facts (type, role, usage, stopReason, bounded errorMessage, tool result
status, `aborted`, responses) put on a queue; the main loop polls the queue
every 0.2 s against the deadline and `cancelled()`. Done = `agent_settled`
(REQ-FUNC-116450ef). On deadline or cancel it sends `abort`, waits the abort
grace for `agent_settled`, closes stdin, waits the exit grace, then
`terminate()`/`kill()` (REQ-REL-0859d96e, REQ-REL-2d48ea39). After settling it
asks `get_session_stats` once (bounded) and only notes a mismatch in evidence.
Rejected alternative: an in-container driver script (keeps `run_command`) -
it would need its own cancel channel and still could not use the Python
fixtures as a fake; findings 2 recommend a host-side client.

**Interfaces and data.** `ContainerManager.spawn(name, argv, env)` builds
`<runtime> exec -i` with exactly `exec`'s env handling (shared helper) and
returns a `subprocess.Popen`; `BoundTarget.spawn(argv, env)` verifies the
pinned identity first. `Executor.run_gate` gains `cancel: Callable[[], bool]`
and `Executor.cancel_grace_seconds(execute)` (default None). `PiExecutor`
(container target = has `spawn`) builds the fixed argv `node <CONTAINER_PI_CLI>
--mode rpc --no-session --no-approve --no-skills --no-extensions
--no-prompt-templates --no-themes --no-mcp -e <CONTAINER_PI_GUARD> --model
<model>` and env `PI_CODING_AGENT_DIR=<CONTAINER_PI_AGENT_DIR>`, `PI_OFFLINE=1`,
`PI_TELEMETRY=0`, `PI_SKIP_VERSION_CHECK=1` (REQ-SEC-a6d32441), constants in
`branding.py`; targets without `spawn` keep the file protocol (RULING-003).
GateRun mapping: completed 0; failed 1 with "Pi run failed (<class>): <msg>"
(REQ-FUNC-1cb4bcc0); protocol failure = process code or 1, spawn errors
127/126 (REQ-REL-12b7dee2); timeout 124 + `timed_out`; cancelled 130. Usage
per REQ-FUNC-7caa53e1, cost 0 / not reported; the orchestrator's
`_journal_usage` is unchanged (RULING-002). Orchestrator passes `cancel` only
when a grace is returned and delays its container-interrupt watcher by the RPC
grace so `abort` comes first.

**Files and test seams.** `docker/Dockerfile.executor-base`,
`docker/verify-runtime.sh`, `docker/pi/adore-guard.ts` (REQ-PLAT-1a1960b2,
live check); `adore/executor/pi_rpc.py`, `launcher.py`, `base.py`,
`adore/isolation.py`, `adore/execution.py`, `adore/branding.py`,
`adore/orchestrator.py`. Tests: `tests/test_pi_rpc.py` with
`tests/fake_pi_rpc.py` replaying `00_Planning/.../fixtures/*.jsonl` (copied to
`tests/fixtures/pi_rpc/` so tests do not depend on planning files); container
spawn argv in `tests/test_isolation.py`; orchestrator cancel wiring and usage
in `tests/test_pi_rpc.py` through the real `_journal_usage` path.

**Risks and open decisions.** Killing the `docker exec` client closes Pi's
stdin (EOF = shutdown) but does not signal the inner process; verified live,
and the orchestrator's interrupt backstop still applies on cancel. Memory
(REQ-NFR-7a10768a): one record at most 16 MiB is buffered; longer records are
skipped (an assistant `message_end` skipped makes tokens unavailable); stream
deltas are not persisted, records over 64 KiB persist as a stub, the file
stops at 32 MiB, tails keep 64 KiB. Base image stays Ubuntu 22.04 with the
official Node 22.23.4 tarball (checksum-verified) instead of switching to
`node:22-bookworm-slim`: same pinned Node without changing the OS that
runtime-project images extend.

**Requirement map.** REQ-PLAT-1a1960b2 image/verify; REQ-FUNC-116450ef
run_pi_rpc + PiExecutor; REQ-FUNC-7caa53e1 reader usage; REQ-REL-0859d96e
abort/terminate; REQ-REL-2d48ea39 cancel + orchestrator; REQ-FUNC-1cb4bcc0
classification; REQ-REL-12b7dee2 protocol failures; REQ-NFR-7a10768a bounded
reader; REQ-SEC-a6d32441 argv/env/guard; REQ-FUNC-59ccdb74 no design impact
beyond the Pi exception.
