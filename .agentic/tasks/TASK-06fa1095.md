## Frame

Problem: System status shows the audit limits as bare zeros (unlimited) so administrators cannot tell what is set, carries two long retention paragraphs, spends a full panel on "Control worker - Ready" and another on storage whose table repeats the same free space for every project because they share one disk (STATED: "valorile actuale din keep for days si audit data limit sa fie pre afisate ... e text descriptiv prea mult ... prea mare o banda ... control worker - ready ... eventual un indicator ... La storage - avem acelasi spatiu pentru fiecare proiect ... daca nu - atunci nu se justifica acest tabel").
Desired outcome: current limits named (Unlimited / N) above the prefilled form, one short impact sentence; worker and storage as compact colored indicators in one row; storage grouped by physical volume - one line when everything shares a disk, a table only for several volumes.
Actors: administrators.
Primary scenario: open System status -> Audit retention with current values and form -> one status row (Control worker: Ready, Storage: Space available) -> "61.8 GiB free of N GiB · ADORE home and all projects share this volume".
Examples: DCP screenshot (0/0 limits, six identical 61.8 GiB rows).
Counterexamples: low-space (<1 GiB) and failed-measurement warnings stay explicit (REQ-PLAT-a1b60ff9); saving 0/blank keeps unlimited (REQ-UX-a8a3e280); the saved notice still reports deleted events (REQ-FUNC-a6d68c4a impact).
In scope: storage API volume_id, System status markup/CSS, copy, tests, requirement, docs.
Out of scope: moving project state roots (answered: state.store_root per project setting; moving data is manual); full suite (STATED: at the end).
Constraints: REQ-PLAT-a1b60ff9 worker readiness must not claim forge/executor/model readiness (the indicator names the Control worker only); impact summary kept as one sentence plus the saved notice.
Success signals: pytest and e2e show volume ids, current values and the compact row; DCP shows them.
Evidence: OBSERVED App.tsx administration block (auditRetentionHelp + auditCopy.impact paragraphs, worker panel, storage panel/table); app.py storage_status returns per-target free/total without a volume identity.
Assumptions: st_dev identifies a physical volume on the host (INFERRED; Linux and Windows both provide it).
Unknowns: none blocking. Decision-blocking questions: none.
Proposed behaviors: B1 named current limits + short impact; B2 compact indicator row; B3 storage grouped by volume (REQ-UX-f41b88d4).
Path and reason: full - backend field and observable UI change.

## Design

- D1 app.py storage_status adds `volume_id` (stat st_dev of the measured path) to each volume entry.
- D2 Audit retention: h2, one short impact sentence (new `auditRetentionShort`), a `Chips` row with Keep for days / Audit data limit as Unlimited or the number, then the unchanged prefilled form; auditRetentionHelp and auditCopy.impact removed.
- D3 one `system-status-row` with two indicators (label + `readiness` pill) for Control worker and Storage; workerReadinessHelp and storageHelp removed.
- D4 storage groups volumes by volume_id: a single group renders one line (free/total GiB + "ADORE home and all projects share this volume"), several groups render a table Volume (items) | Free | Status; low and failed states keep their warnings.
- Test seams: tests/test_web_storage.py (volume_id), e2e/audit.spec.ts System status assertions.
