## Frame

Problem: in Administration > Change history (and project History) expanding an event's evidence opens it inside the last table cell, so the automatic table layout resizes every column - a large visual jump; the evidence lists a 64-character operation correlation and "Not recorded" base/candidate revisions for events where they never apply (STATED: "cand expandez evidenta - intreg formatul se modifica ... fluctuatie mare ... se poate ... sa nu se schimbe asa mult? ... poate pe un user nu-l intereseaza ID operatie (sau ... numai o parte din ID ca la git) ... ce rol au base revision si candidate revision? Avem nevoie de ele?").
Desired outcome: evidence opens in a full-width row below the event; columns keep their widths; correlations/revisions shortened to 12 characters (full value on hover); base/candidate revision rows only when recorded.
Actors: administrators and authorized project-history readers.
Primary scenario: Change history -> Evidence on an event -> detail row under it with Before, After, Operation (short), Base/Candidate (short, if recorded) -> table columns do not move.
Examples: DCP screenshot (readiness-checked event with 64-char operation and Not recorded revisions).
Counterexamples: legacy "Before/After value not recorded" stays explicit; filters, paging, counts and validation unchanged; backend evidence unchanged (REQ-DATA-34ed1530).
In scope: AuditHistory.tsx markup, CSS, e2e, requirement, docs.
Out of scope: audit API and recording; full suite (STATED: at the end).
Constraints: base/candidate revisions are the configuration SHA-256 a change was prepared against and the proposed configuration - they matter for configuration prepare/apply/discard events only (answer to the user).
Success signals: e2e shows stable column positions and shortened ids; DCP shows it.
Evidence: OBSERVED AuditHistory.tsx renders <details> in the Evidence cell with all five fields; styles.css .audit-evidence rules.
Assumptions: 12 characters, as in short Git hashes, identify an event well enough for reading; the full value stays available (INFERRED).
Unknowns: none blocking. Decision-blocking questions: none.
Proposed behaviors: B1 detail row and fixed column widths; B2 shortened ids with full title; B3 revisions only when recorded (REQ-UX-0ce1d7d9).
Path and reason: full - observable UI change with a new requirement.

## Design

- D1 AuditHistory: the Evidence cell holds a toggle button (aria-expanded/aria-controls); an expanded event adds `tr.audit-detail-row` with one `td colSpan=5` holding the `dl` (two-column grid).
- D2 CSS: `.audit-evidence table { table-layout: fixed }` with column widths (who/what/when/result/evidence), detail row grid, long values wrap.
- D3 short ids: `short(hex)` = first 12 characters inside `<code title=full>`; numeric operation ids render as `#n`; base/candidate entries render only when non-null.
- Test seams: e2e/audit.spec.ts new routed evidence test; existing evidence clicks keep working through the button text.
