## Frame

Problem: ADORE uses about 15 labels per project (all named in its configuration) but creates none of them. On GitHub and Gitea a label that does not exist in the repository cannot be added to a ticket, so users must create every label by hand before ADORE works; GitLab creates missing labels on first use without colour or description. STATED: "putem avea o functie la enroll repository - la final - sa creeze labeluri adore (cele definite pe proiect) in forge? Ar ajuta user-ul sa aibe etichetele deja facute - eventual cu verificare daca deja sunt sa nu le mai creeze." and the choices "Enrollment + Settings (Recommended)" (a checkbox on by default in Review and create, plus a Create missing labels button in Settings → Repository) and "All ADORE labels (Recommended)".
Desired outcome: at the end of enrollment (and Clone project config), and on demand in Settings → Repository, ADORE reads the repository's labels and creates only the missing ADORE labels with a colour and a short description, then reports created, already existing and failed labels; existing labels are never changed or deleted.
Actors: administrators.
Primary scenario: Enroll new project with Create the ADORE labels ticked -> project created -> the result shows 15 created on a new Gitea repository; a second run reports all existing.
Examples: labels agent-ready, agent-working, agent-clarify, agent-answered, agent-mr, agent-failed, agent-done, agent-hold, no-agent, P1, P2, P3, bug (type_bug), agent-approved, agent-revise, agent-quick and the workflow.kind_labels names.
Counterexamples: no renaming, recolouring or deletion of existing labels; reserved/hidden label settings (type_feature, executor prefix) are not created; label creation failure never undoes project creation.
In scope: label specification and ensure logic, forge adapter list/create for GitHub, GitLab, Gitea, an administrator endpoint, the wizard option and result, the Settings button and result, four-locale copy and help, tests, docs, CHANGELOG, release notes, DCP deploy.
Out of scope: label colours chosen by the user; syncing renamed labels (a new name is created, the old one is left); full suite (STATED: tests only at the end, targeted runs now).
Constraints: forge commands through the project's credential-scoped runner (same as ticket reads); label names compared case-insensitively; bounded paging.
Success signals: targeted pytest and e2e green; on DCP the Gitea repository gets the labels once.
Evidence: OBSERVED forge adapters wrap `gh api`, `glab api`, `tea api` with paging helpers; ticket endpoints build the forge with `open_forge(config, project_runner(...))`; no label creation exists; LabelsConfig defines lifecycle, selection, control labels; delivery.approval_label, review.revise_label, workflow.quick_label and workflow.kind_labels name other labels.
Assumptions: INFERRED the server's forge account may create labels (repository write/maintainer); otherwise each label is reported as failed with the forge's reason.
Unknowns: none blocking.
Decision-blocking questions: answered (STATED above).

## Design

- D1 `adore/forge_labels.py`: `project_labels(config) -> list[LabelSpec(name, color, description)]` from lifecycle (7), control hold/exclude, selection priority high/medium/low and type_bug, delivery.approval_label, review.revise_label, workflow.quick_label and workflow.kind_labels names; unique by case-insensitive name, empty names skipped; fixed colours per group and English descriptions. `ensure_labels(forge, specs) -> {created, existing, failed[{name, reason}]}`: one bounded listing, then a create per missing label; a create failure is recorded and the others continue; a listing failure fails the whole call.
- D2 Forge adapters: `list_labels() -> list[str]` and `create_label(name, color, description)`. GitHub `gh api repos/<repo>/labels` (paged) and `gh api --method POST repos/<repo>/labels -f name -f color(no #) -f description`; GitLab `glab api projects/<id>/labels` (paged) and POST with `--raw-field name/color(#)/description`; Gitea `tea api GET repos/<repo>/labels?limit=50&page=N` and POST with fields.
- D3 `POST /api/v1/projects/{name}/labels/ensure` (administrator, CSRF): builds the forge like ticket reads, returns the report, audits `labels-ensured` with counts; 503 with a coded error when the forge cannot be read.
- D4 UI: Review and create gets "Create the ADORE labels in the repository (missing ones only)", ticked by default (also in Clone project config); after a successful creation the wizard calls D3 for the new project and shows the report on the created screen (a failure is shown, the project stays created). Settings → Repository gets "Create missing labels" with the same report. Copy in four locales.
