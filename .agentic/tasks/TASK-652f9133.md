## Frame

Problem:
- STATED (ticket #62 Goal): configuration/CLI users need ADORE to conduct
  tickets in repositories without `.agentic/aegis.py`, without installing AEGIS.
- OBSERVED (`adore/orchestrator.py::_probe_repository_payload`, `poll_once`,
  `_conduct`; all source paths below are under `04_Software/`): admission
  currently probes AEGIS unconditionally and conduction creates/probes a task.
  `RunState` has no workflow discriminator. This establishes the present
  implementation boundary, not a claim about any live deployment.

Desired outcome:
- STATED (ticket Goal, Done when): an eligible CLI/configured ticket in an
  AEGIS-free repository reaches `done` / `awaiting-approval` through a bounded
  fresh direct Pi session, with genuine product changes, no open questions and
  an explicitly unverified candidate. Existing human approval, publication and
  review authority remain intact; AEGIS repositories retain their existing path.

Actors:
- STATED (ticket and root AGENTS.md): operator/configuration and CLI caller;
  ADORE conductor, durable state store and isolation backend; Pi executor;
  forge adapters/ticket commenters; human candidate approver and merger.

Primary scenario:
1. STATED (ticket Detection, Run state; plan sections 1 and 4.1): pre-pick
   checks the clone for the payload, probing only when present; the claimed
   run records its immutable `workflow` from its worktree. An absent payload
   selects direct, starts at `build`, and has no active or historical task id.
2. STATED (ticket Branch point, Sessions, Prompt): after provision, direct
   conduction uses its own method and a file-backed prompt carrying the ticket,
   repository-instruction guidance, authority limits, questions path and summary
   request. Each attempt uses a fresh Pi session and existing limits/backends.
3. STATED (ticket Done): after a settled successful session with no questions
   and a changed product fingerprint, retain the summary, remove its exchange
   file, checkpoint the candidate, record not-configured validation evidence and
   its fingerprint, and present it at `done` / `awaiting-approval`.
4. STATED (ticket Ticket and MR/PR texts): approval and publication show the
   summary, changed-file count, and exactly "Verification: not configured. This
   candidate is unverified." No direct presentation has an AEGIS task line.
5. STATED (plan 4.7 and ticket Goal): approval remains fresh and candidate-bound;
   ADORE publishes through its existing forge adapter and never merges.

Examples:
- STATED (ticket Done when): a fake executor makes a real product edit and
  writes `ADORE_SUMMARY.md`; one direct session reaches approval and both the
  approval comment and subsequently published MR/PR carry that summary and the
  unverified notice, never the exchange files.
- STATED (ticket Done when): a blocking questions file parks the run;
  `agent-answered` resumes it in a new direct session receiving the thread.
- STATED (ticket Detection): a supported installed payload still uses AEGIS.
