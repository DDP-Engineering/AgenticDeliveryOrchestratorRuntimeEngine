## Frame

Problem: configuration edits do not keep a file's line endings. The shared
  scalar editor `_set_toml_scalar` (04_Software/adore/cli.py) and the local
  endpoint editor `_set_endpoint` (04_Software/adore/web/app.py) rejoin lines
  with LF and append LF text to a CRLF file. The web staging and direct edit
  paths then write the candidate with `Path.write_text`, which on Windows turns
  each existing CR LF into CR CR LF; tomllib rejects the result, so staging a
  key whose table is absent from a CRLF file answers 400 invalid_config. The CLI
  `config set` reads with `read_text` and writes with `write_text`, so on
  Windows it rewrites every line ending of the file.
Desired outcome: CLI and web configuration edits work on CRLF and LF files on
  every OS and keep the file's line-ending style; no carriage return is added
  or lost.
Actors: administrator editing settings in the web UI; operator running
  `adore config set`; Windows development hosts and Windows ADORE hosts.
Primary scenario: a project's config.toml uses CRLF -> an administrator stages
  `polling.poll_interval_seconds = 60` (table absent) -> staging validates and
  succeeds -> applying writes a file that still uses CRLF throughout.
Examples: CRLF file + new table -> staged and applied, every line CRLF; CRLF
  file + existing key replaced -> still CRLF; LF file edited on Windows by
  `adore config set` -> still LF.
Counterexamples: an LF file never gains CR; comments and other lines stay
  untouched (existing guarantee).
In scope: `_set_toml_scalar`, `_set_endpoint`, the candidate/live writes in
  `_candidate_config_edit` and `config_update` (web/app.py) and
  `_config_set_locked` (cli.py); regression tests with explicit CRLF bytes;
  CHANGELOG.
Out of scope: TOML import (writes the uploaded text as given), the profile
  wizard's own file writing, normalizing existing files.
Constraints: offline tests; tests use explicit CRLF bytes so they fail on
  every OS before the fix; existing edit, validation and lock behavior
  unchanged.
Success signals: tests show CRLF files staged, applied and edited by the CLI
  keep CRLF with no CR CR LF, and LF files stay LF.
Evidence:
  - STATED: task note "Fix CRLF config edits failing on Windows" (found in
    TASK-2b9eda6e); the user asked to do it here.
  - OBSERVED: `04_Software/adore/web/app.py` `_candidate_config_edit` decodes
    the bytes and writes `candidate.write_text(changed, encoding="utf-8")`;
    `config_update` does the same for the live candidate; apply writes

  - OBSERVED: `04_Software/adore/cli.py` `_set_toml_scalar` uses `splitlines()`
    and `"\n".join`, and for an absent table returns the original text plus
    LF-separated lines; `_config_set_locked` uses `read_text`/`write_text`.
  - OBSERVED: reproduced in TASK-2b9eda6e: a CRLF file staging

  - INFERRED: Linux hosts (DCP) never double CRs, but `_set_toml_scalar` still
    turns a CRLF file into LF when it replaces a key there.
Assumptions: a file's style is CRLF when it contains CR LF, otherwise LF.
Unknowns: none.
Decision-blocking questions: none.
Proposed behaviors:
  1. Editing a configuration value from the CLI or the web keeps the file's
     line-ending style (CRLF or LF) for every line, including added ones.
  2. Configuration text is read and written as bytes, so the OS never
     translates line endings; a CRLF file can be staged, applied and edited
     on Windows.

## Design

- **Line ending rule (REQ-PLAT-722173c8).** A small helper in `adore/cli.py`
  returns `"\r\n"` when the text contains a CR LF, else `"\n"`;
  `_set_toml_scalar` and `_set_endpoint` (web/app.py imports the CLI helper
  set already) use it.
- **`_set_toml_scalar`.** Split on LF only (`text.split("\n")`) instead of
  `splitlines()`, so each line keeps its own trailing CR and the join with LF
  restores every untouched line byte for byte (also stops `splitlines()` from
  splitting on other Unicode line separators inside values). Matching uses the
  line without its CR (`_inline_comment` returns to end of line, so the CR must
  not reach the comment). A replaced line keeps its own ending; an inserted
  line gets the file's ending; after an unterminated header the header gets
  the ending and the new line becomes the unterminated last line; an absent
  table is appended with the file's ending.
- **`_set_endpoint`.** The inline `runtime_env` rewrite splits on LF, builds
  the new `[container.runtime_env]` section with the file's ending, and joins
  the remaining lines unchanged (fix cycle 2 replaced the old `rstrip()` join,
  which dropped trailing spaces and blank lines at the end of the file), adding
  the file's ending only when the text has no final newline.
- **Byte I/O.** `_candidate_config_edit` and `config_update` write the
  candidate with `write_bytes(changed.encode("utf-8"))`; `_config_set_locked`
  reads `read_bytes().decode("utf-8")` and writes the temp file with
  `write_bytes`. Apply already writes bytes. Text-mode reads translate CR LF
  to LF on every OS and text-mode writes add CR on Windows; bytes avoid both.
- **Tests.** New `tests/test_config_line_endings.py`: exact-text unit cases
  for `_set_toml_scalar` (CR LF and LF; replace with comment, insert,
  absent table, unterminated header and key); CLI `config set` on CR LF and
  LF files (existing key and absent table); web stage+apply of an absent
  table, direct edit and endpoint edit on CR LF and LF files
  (parametrized). Explicit bytes make the tests fail on every OS before the
  fix (Linux: CR LF lost or mixed; Windows: CR CR LF refused, LF gains CR).
- **Compatibility.** No interface, data or dependency change; files that
  were LF stay LF; files that were CR LF stop being converted. Import and the
  wizard are out of scope (Frame).
- **Alternatives.** Normalizing every config to LF was rejected: it changes
  untouched lines and fights editors on Windows hosts.
